# Reflection: scaling from ~280 codes to 50,000

The biggest change is that **top-k vector similarity alone stops being good enough**. At 280 codes the embedding space is sparse and well-separated, so `top-k=5` reliably surfaces the right entry. Real ICD-11 has tens of thousands of fine-grained, near-duplicate codes (laterality, staging, "other specified" variants), so a flat semantic search over the whole catalog would return a cluster of plausible-looking neighbors without the specific right one in the top 5 — we already saw an early version of this failure mode at 288 codes (the TIA case in `EVAL_CASES.md`, where the target code didn't make the top-5 catalog matches even though a related code did). At 50k codes this would be the dominant failure mode, not the exception.

The fix is a two-stage or hybrid retrieval: first narrow by chapter/block (ICD-11's own hierarchy — already captured in `IcdCatalogEntry.chapter` but currently unused for filtering), then do vector search within that narrower set, likely combined with lexical/keyword matching (BM25) and a reranking pass, since embeddings alone are weak at discriminating between near-identical clinical descriptions. `top-k` would also need to grow substantially for the shortlist handed to the proposal agent, which raises prompt size/cost and puts more weight on the verification step to catch a plausible-but-wrong-specificity code.

Ingestion also changes: the current `VectorStoreIngestionRunner` loads everything into memory and does one bulk `vectorStore.add()`, with a simple "table has any rows → skip" idempotency guard. At 50k that needs batching/streaming, and the guard needs to become incremental (diff against a source-of-truth version/checksum per code) so a catalog update re-embeds only what changed rather than requiring a full re-ingest — important both for cost (if using a paid embedding API) and for staying current as ICD-11 codes get revised.
